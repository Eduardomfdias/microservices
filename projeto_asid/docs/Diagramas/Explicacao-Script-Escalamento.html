Objetivo do Script

O que faz e porquê

O script experimentos_escalamento.sh automatiza a medição do ponto de quebra do sistema Online Boutique em Kubernetes. O objetivo é descobrir a partir de quantos utilizadores simultâneos o sistema começa a degradar — seja por alta latência ou por erros de resposta.

Configuração Global

Variáveis e inicialização

O que faz

Define as variáveis globais usadas por todo o script. Todas podem ser substituídas por variáveis de ambiente antes de correr o script.

  • FRONTEND_URL — endereço do sistema a testar (por omissão: localhost)
  • RESULTS_DIR — cria uma pasta nova com data/hora para guardar todos os resultados
  • log() — função auxiliar que imprime mensagens com timestamp e guarda no ficheiro run.log
Cada execução cria uma pasta própria, por exemplo resultados_20260308_180646/, para não sobrescrever resultados anteriores.
experimentos_escalamento.sh — linhas 13–17 
# URL do frontend (pode ser substituído)
FRONTEND_URL="${FRONTEND_URL:-http://localhost}"

# Pasta de resultados com data/hora única
RESULTS_DIR="resultados_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$RESULTS_DIR"

# Função de logging com timestamp
log() {
  echo "[$(date +%H:%M:%S)] $*" | tee -a "$RESULTS_DIR/run.log"
}

Verificação de Pré-Requisitos

Função: check_prerequisites()

O que faz

Antes de iniciar qualquer teste, verifica se as ferramentas necessárias estão disponíveis e funcionais:

  • kubectl cluster-info — confirma que o Kubernetes está acessível. Se falhar, o script termina com erro.
  • kubectl top nodes — verifica se o metrics-server está instalado. Se não estiver, instala-o automaticamente e aguarda 60 segundos para arrancar.
  • which locust / find ~/Library/Python — localiza o binário do Locust. No macOS, o pip instala o locust em ~/Library/Python e não no PATH padrão do sistema, por isso é necessária esta pesquisa manual.
O Locust é instalado pelo pip em ~/Library/Python/3.x/bin/locust, fora do PATH normal do bash/zsh. Por isso o script usa find para localizá-lo.
linhas 22–45 
check_prerequisites() {
  # 1. Kubernetes acessível?
  kubectl cluster-info > /dev/null 2>&1 || {
    log "ERRO: kubectl não conectado"
    exit 1
  }

  # 2. metrics-server instalado?
  kubectl top nodes > /dev/null 2>&1 || {
    log "A instalar metrics-server..."
    kubectl apply -f https://...components.yaml
    sleep 60
  }

  # 3. Localiza locust (não está no PATH no macOS)
  LOCUST_BIN=$(which locust 2>/dev/null)
  if [ -z "$LOCUST_BIN" ]; then
    LOCUST_BIN=$(find ~/Library/Python \
      -name "locust" -type f | head -1)
  fi

  # 4. Se ainda não encontrou, instala
  if [ -z "$LOCUST_BIN" ]; then
    pip3 install locust faker --quiet
    LOCUST_BIN=$(find ~/Library/Python \
      -name "locust" -type f | head -1)
  fi

  export LOCUST_BIN
  log "Pré-requisitos OK"
}

Captura de Baseline

Função: capture_baseline() — fotografia do cluster sem carga

O que faz

Antes de gerar qualquer carga, o script regista o estado inicial do cluster. Isto é essencial para comparar o comportamento do sistema com e sem carga.

  • kubectl get deployments -o json — lista todos os serviços com as suas configurações de CPU e memória (requests e limits)
  • kubectl top pods — consumo de CPU e RAM de cada pod em repouso
  • kubectl top nodes — consumo do nó Kubernetes
  • kubectl get hpa — verifica se existe Horizontal Pod Autoscaler (escalamento automático). Na fase baseline não deve haver nenhum.
Todos os ficheiros são guardados em resultados_xxx/baseline/ para referência futura na análise dos resultados.
linhas 50–83 
capture_baseline() {
  local out="$RESULTS_DIR/baseline"
  mkdir -p "$out"

  # Configuração de todos os deployments
  kubectl get deployments -o wide \
    > "$out/deployments.txt"

  # Tabela: serviço, réplicas, CPU/RAM req e limit
  kubectl get deployments -o json | python3 -c "
    # processa JSON e imprime tabela formatada
    # com CPU request, CPU limit, Mem request, Mem limit
  " | tee "$out/resources_config.txt"

  # Consumo real de CPU e RAM (sem carga)
  kubectl top pods --sort-by=cpu \
    > "$out/top_pods_idle.txt"
  kubectl top nodes \
    > "$out/top_nodes_idle.txt"

  # Estado de todos os pods
  kubectl get pods -o wide \
    > "$out/pods_status.txt"

  # Verificação de auto-scaling (HPA)
  kubectl get hpa \
    > "$out/hpa_inicial.txt"
}

Monitorização Contínua em Background

Funções: start_monitoring() / stop_monitoring()

O que faz

Lança um processo filho (em background) que vai recolhendo métricas do cluster de 10 em 10 segundos, enquanto os testes de carga correm em paralelo.

  • kubectl top pods — a cada 10s, regista CPU e RAM de todos os pods no ficheiro pods_metrics.csv
  • kubectl get pods — verifica se algum pod reiniciou (crash/OOMKill) e regista em restarts.log
  • & (background) — o processo de monitorização corre em paralelo ao Locust, sem bloquear os testes
  • monitor.pid — guarda o ID do processo para o poder terminar no fim com stop_monitoring()
O sinal & no final do bloco ( ... ) & lança o subshell em background. O PID é guardado em $MONITOR_PID para ser terminado mais tarde com kill.
linhas 88–120 
start_monitoring() {
  local interval=${1:-10}  # seg entre snapshots
  local out="$RESULTS_DIR/monitoring"
  mkdir -p "$out"

  # Subshell em BACKGROUND com &
  (
    i=0
    while true; do
      ts=$(date +%H:%M:%S)

      # CPU e RAM de todos os pods → CSV
      kubectl top pods 2>/dev/null | \
        awk -v ts="$ts" -v i="$i" \
        'NR>1{print ts","i","$1","$2","$3}' \
        >> "$out/pods_metrics.csv"

      # Detecção de restarts/crashes
      kubectl get pods --no-headers | \
        awk -v ts="$ts" \
        '$4>0{print ts" RESTART "$1" x"$4}' \
        >> "$out/restarts.log"

      i=$((i+1))
      sleep "$interval"
    done
  ) &  # ← corre em paralelo

  MONITOR_PID=$!
  echo $MONITOR_PID > "$RESULTS_DIR/monitor.pid"
}

stop_monitoring() {
  kill "$(cat "$RESULTS_DIR/monitor.pid")"
}

Ficheiro de Testes Locust

Função: create_locustfile() — define o comportamento dos utilizadores virtuais

O Locust é a ferramenta de load testing usada. O script cria automaticamente um ficheiro Python que define como cada utilizador virtual se comporta — que páginas visita e com que frequência.

Parâmetros principais

  • wait_time = between(0.5, 1) — cada utilizador espera entre 0.5 e 1 segundo entre pedidos. Simula utilizadores frequentes (ex: Black Friday).
  • @task(peso) — define a frequência relativa de cada ação. O peso 10 significa que "ver produto" é chamado 10x mais do que "checkout".

from locust import HttpUser, task, between
import random

PRODUCT_IDS = [
    "OLJCESPC7Z", "66VCHSJNUP", "1YMWWN1N4O",
    "L9ECAV7KIM", "2ZYFJ3GM2N", "0PUK6V6EV0",
    "LS4PSXUNUM", "9SIQT8TOJO", "6E92ZMYYFZ"
]

class OnlineBoutiqueUser(HttpUser):
    # Espera 0.5–1s entre pedidos (simulação realista)
    wait_time = between(0.5, 1)

    @task(10)  # mais frequente
    def browse_product(self):
        pid = random.choice(PRODUCT_IDS)
        self.client.get(f"/product/{pid}")

    @task(5)
    def index(self):
        self.client.get("/")

    @task(3)
    def add_to_cart(self):
        pid = random.choice(PRODUCT_IDS)
        self.client.post("/cart",
            data={"product_id": pid, "quantity": "1"})

    @task(1)  # menos frequente mas mais pesado
    def checkout(self):
        pid = random.choice(PRODUCT_IDS)
        # Garante item no carrinho antes do checkout
        self.client.post("/cart",
            data={"product_id": pid, "quantity": "1"})
        self.client.post("/cart/checkout", data={
            "email": "test@asid.uc.pt",
            "credit_card_number": "4432801561520454",
            "credit_card_cvv": "672",
            # ... restantes campos
        })

Algoritmo de Ponto de Quebra

Função: find_breaking_point() — núcleo do script

Esta é a função principal do script. Começa com 1 utilizador virtual e vai incrementando 1 por step, até o sistema quebrar ou atingir o limite máximo de utilizadores.

ParâmetroValor padrãoSignificado
STEP_DURATION60sDuração de cada step com N utilizadores
COOLDOWN15sPausa entre steps para o sistema estabilizar
P99_THRESHOLD2000msp99 acima deste valor = latência inaceitável
FAIL_THRESHOLD5%Taxa de erros acima deste valor = quebra
MAX_USERS60Limite de segurança (para não correr indefinidamente)

Critérios de Quebra

Após cada step, um script Python analisa o CSV gerado pelo Locust e verifica duas condições:

  • QUEBRA_FALHAS — mais de 5% dos pedidos resultaram em erro HTTP (4xx, 5xx, timeout). Indica que o sistema está a rejeitar pedidos.
  • QUEBRA_LATENCIA — o percentil 99 da latência ultrapassou 2000ms. Indica que 1% dos utilizadores esperam mais de 2 segundos.
p50/p90/p99 são percentis de latência. Por exemplo, p99=500ms significa que 99% dos pedidos foram respondidos em menos de 500ms. O p99 é o indicador mais sensível — sobe muito antes do p50.
linhas 344–428 
for users in $(seq 1 1 "$MAX_USERS"); do

  # Corre Locust headless durante STEP_DURATION
  "$LOCUST_BIN" \
    --locustfile "$RESULTS_DIR/locustfile.py" \
    --host "$FRONTEND_URL" \
    --users "$users" \
    --spawn-rate "$users" \
    --run-time "${STEP_DURATION}s" \
    --headless \
    --csv "$out/locust" \
    --html "$out/report.html"

  # Snapshot de CPU/RAM após o step
  kubectl top pods > "$out/top_pods.txt"

  # Analisa CSV com Python: p99 e taxa de falhas
  result=$(python3 - "$out/locust_stats.csv" \
    "$P99_THRESHOLD" "$FAIL_THRESHOLD" << 'PYEOF'
  # se fail_pct >= 5% → QUEBRA_FALHAS
  # se p99 >= 2000ms  → QUEBRA_LATENCIA
  # senão             → OK
PYEOF)

  # Para se encontrou quebra
  if [[ "$status" == QUEBRA* ]]; then
    log "PONTO DE QUEBRA: ${users} users"
    break
  fi

  # Pausa para o sistema estabilizar
  sleep "$COOLDOWN"
done

Relatório Final

Função: generate_report()

O que produz

No final de todos os steps, consolida os resultados num ficheiro de texto RESUMO_EXPERIMENTOS.txt. Para cada fase executada mostra:

  • Total de pedidos realizados
  • Número e percentagem de falhas
  • Latências p50, p90, p99
  • Throughput (RPS)
O Locust também gera automaticamente um report.html interactivo por step, com gráficos de latência e throughput ao longo do tempo.

Modos de Execução

Função: main() — como invocar o script
ComandoO que faz
./experimentos_escalamento.sh incremental Modo principal — 1 user, 2, 3... até quebrar. Recomendado.
./experimentos_escalamento.sh baseline Só captura o estado inicial do cluster (sem testes de carga).
./experimentos_escalamento.sh monitor Só activa a monitorização contínua (útil para observar o cluster manualmente).
./experimentos_escalamento.sh report Gera o resumo final a partir de resultados já existentes.

Variáveis opcionais

Podem ser passadas como prefixo ao comando para ajustar o comportamento:

# Teste mais longo com mais utilizadores e critérios mais permissivos
MAX_USERS=80 \
STEP_DURATION=90 \
P99_THRESHOLD=3000 \
FAIL_THRESHOLD=2 \
./experimentos_escalamento.sh incremental
